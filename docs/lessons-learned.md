# 작업 회고: 실수와 교훈 (2026-11-09)

이 문서는 2026-11-09 하루 동안 진행한 작업(이슈 #1~#3 검증·수정, QA와 이슈 #4~#8, 목록·로딩·속도 개선, GA4·GTM 연동)에서 나온 실수와 교훈을 정리한 기록입니다. 관련 커밋은 `1df774a`부터 `456b0ad`까지입니다.

각 항목은 무슨 일이 있었는지, 어떤 영향이 있었는지, 다음에는 어떻게 할지를 순서대로 적었습니다.

## 1. 검증과 판정

### 1-1. 셸 따옴표 때문에 검사 결과가 거짓으로 나옴

- **무슨 일**: 002번 원고 초록에 `$r\in\{0,1\}$`이 있는지 `node -e '...'`로 확인했는데, 셸을 거치며 백슬래시가 빠져 `false`가 나왔습니다. 스크립트 파일로 다시 돌리자 `true`였습니다.
- **영향**: 그대로 믿었다면 해결된 이슈를 미해결로 보고할 뻔했습니다.
- **교훈**: 백슬래시나 `$`가 들어간 문자열 검사는 인라인 명령 대신 파일로 된 스크립트에서 `String.raw`로 합니다. 예상과 다른 결과가 나오면 판정하기 전에 검사 방법부터 의심합니다.

### 1-2. 확인용 실행이 작업 트리를 바꿈

- **무슨 일**: 재현성을 확인하려고 `build-catalog.mjs`를 옵션 없이 실행해 `data/catalog.json`이 바뀐 채 남았습니다.
- **교훈**: 검증용 실행은 `--output=../tmp.json`처럼 저장소 밖으로 내보냅니다. 실행이 끝나면 `git status`가 깨끗한지 확인합니다.

## 2. 커밋 관리

### 2-1. 여러 이슈의 변경을 한 파일에서 섞어 스테이징함

- **무슨 일**: `app.js`에 이슈 #2와 #3 수정이 함께 있는데 `git add app.js`로 통째로 올렸습니다. 되돌린 뒤 `-U0` 패치를 덩어리별로 골라 적용해 커밋을 나눴습니다.
- **추가 실수**: `git rm`으로 이미 지운 `components.css`를 다시 `git add`에 넣어 pathspec 오류가 났습니다.
- **교훈**: 이슈별로 커밋할 계획이면 파일 하나를 고칠 때마다 바로 커밋하거나, 처음부터 덩어리 단위로 스테이징합니다. 커밋 직전에는 `git diff --cached`로 범위를 확인합니다.

### 2-2. 커밋하기 전 작업 트리를 배포함

- **무슨 일**: Cloudflare 배포용 `dist`를 커밋 전의 작업 트리에서 만들어 올렸습니다. 결과적으로 내용은 같았지만, 커밋되지 않은 상태가 운영에 나갈 수 있는 순서였습니다.
- **교훈**: 운영 배포는 커밋한 뒤 `git archive HEAD`로 만든 결과물로 합니다. 작업 트리에서 만든 결과물은 미리보기(`--branch qa`)에만 씁니다.

## 3. 배포와 측정

### 3-1. 배포 가능한지 확인하지 않고 GitHub Pages를 권장함

- **무슨 일**: 저장소가 private이고 요금제가 Pages를 지원하지 않는다는 것을 확인하지 않은 채 "GitHub Pages 켜기"를 권장안으로 제시했다가 HTTP 422로 실패했습니다. 질문을 한 번 더 해야 했습니다.
- **교훈**: 선택지를 내밀기 전에 실행할 수 있는지부터 확인합니다(`gh api repos/... --jq .visibility`, Pages API 호출).

### 3-2. 빌드가 끝나기 전에 측정해 개선 전 점수를 잃음

- **무슨 일**: GitHub Pages를 켠 직후 PageSpeed Insights로 측정해 404 페이지를 쟀습니다. 다시 재기 전에 개선 코드가 배포돼 GitHub Pages의 개선 전 점수는 남지 않았습니다.
- **교훈**: 측정 전에 대상 URL이 200을 돌려주고 실제 콘텐츠를 내보내는지 `curl`로 먼저 확인합니다. 개선 전 측정은 코드를 바꾸기 전에 끝냅니다.

### 3-3. 측정 도구가 멈추고 흔들림

- **무슨 일**:
  - PageSpeed Insights API는 키 없이 호출해 일일 할당량을 넘었습니다.
  - 웹 버전은 앱 브라우저 패널이 숨겨진 동안 30분 넘게 "분석 실행 중"에서 멈췄습니다.
  - 대신 쓴 로컬 Lighthouse는 같은 코드인데 모바일 성능이 72~93으로 크게 흔들렸습니다.
- **교훈**: 측정은 공개 측정 사이트에서 하되, 화면이 보이는 브라우저에서 돌립니다. 로컬 Lighthouse는 원인을 찾는 데만 쓰고 점수 근거로는 쓰지 않습니다.

### 3-4. 원인을 확인하지 않고 고쳐서 수치가 나빠짐

- **무슨 일**: 진단 항목에 나온 KaTeX 지연 로딩만 먼저 적용했더니 모바일 Speed Index가 3.6초에서 3.8초로 늘었습니다. 실제 원인은 첫 목록 렌더링이 상세 패널 전용 `youtube.json`까지 기다리는 구조와 CSS 2개의 직렬 로딩이었습니다. 이 둘을 고친 뒤에야 0.8초가 됐습니다.
- **교훈**: 고치기 전에 LCP 분석, 네트워크 종속 트리, 첫 렌더링 전에 기다리는 요청 목록을 먼저 봅니다. 수치를 움직이는 원인을 찾은 다음에 수정합니다.

### 3-5. 한 수정이 다른 감점을 만듦

- **무슨 일**: `404.html`을 추가하자, 그동안 메인 페이지로 대신 응답되던 `/favicon.ico`가 404를 내면서 콘솔 오류가 생겼습니다. 이 때문에 Lighthouse 권장사항 점수가 100에서 96으로 떨어졌습니다.
- **교훈**: 라우팅이나 404 동작을 바꾸면 브라우저가 자동으로 요청하는 경로(`/favicon.ico`, `/robots.txt` 등)를 함께 점검합니다.

### 3-6. QA용 미리보기 배포를 정리하지 않음

- **무슨 일**: `qa.openai-math-study.pages.dev` 미리보기 배포가 공개된 채 남아 있습니다.
- **교훈**: 검증용 배포는 작업이 끝나면 지우거나, 남긴다는 사실을 작업 기록에 적습니다.

## 4. 테스트

### 4-1. 테스트 쪽 결함을 앱 버그로 의심함

- **무슨 일**: E2E 실패 두 건이 테스트 결함이었습니다.
  - 해시만 바꾼 `page.goto`는 페이지를 새로 불러오지 않아 "없는 딥링크" 검사가 실패했습니다.
  - 무한 스크롤 검사는 `mouse.wheel`과 페이지의 `scroll-behavior: smooth`가 겹쳐 실패했습니다.
- **교훈**: 실패가 나오면 새 컨텍스트에서 최소 재현을 먼저 해 봅니다. 스크롤은 `scrollTo({ behavior: "instant" })`로 하고, 해시 내비게이션 뒤에는 `reload`를 넣습니다.

### 4-2. CSS 선언 순서 실수

- **무슨 일**: `.skeleton-line`을 `.skeleton`보다 앞에 선언해 `min-height`가 덮어써졌습니다. 테스트 전에 발견해 `.skeleton.skeleton-line`으로 고쳤습니다.
- **교훈**: 수정 클래스를 추가할 때는 같은 우선순위의 기존 규칙과 순서를 확인합니다.

## 5. 외부 서비스 설정(GA4·GTM)

### 5-1. 사용자와 같은 브라우저 패널을 동시에 조작함

- **무슨 일**: GA4 속성 만들기 도중 사용자 클릭과 제 클릭이 겹쳐 "종료하시겠습니까?" 창이 뜨고 작업이 홈으로 나갔습니다.
- **교훈**: 공유 브라우저 패널을 조작하기 전에 "제가 조작하는 동안 클릭하지 말아 주세요"라고 먼저 알립니다. 로그인처럼 사용자 차례인 단계는 끝났다는 신호를 받은 뒤 시작합니다.

### 5-2. 입력값을 확인하지 않음

- **무슨 일**: GTM 측정 ID 칸에 자동완성이 끼어들어 엉뚱한 ID(`G-JX411LJZ48`)와 이벤트 이름이 붙은 값이 들어갔습니다. Escape를 누르자 "저장되지 않은 변경사항" 창이 떴습니다.
- **교훈**: 외부 콘솔에 값을 입력한 뒤에는 DOM에서 실제 값을 읽어 확인하고 나서 저장합니다. 편집 패널에서는 Escape로 목록을 닫지 않고 빈 곳을 클릭합니다.

### 5-3. 게시 승인을 미리 받지 않음

- **무슨 일**: GTM 컨테이너 '게시' 클릭이 권한 검사에서 "요청하지 않은 게시"로 막혀 한 번 더 질문해야 했습니다.
- **교훈**: 외부 서비스에서 되돌리기 어려운 동작(게시, 약관 동의, 운영 반영)은 설정을 시작할 때 한 번에 범위를 정해 승인을 받습니다.

### 5-4. 주요 이벤트 지정이 바로 되지 않는다는 것을 예상하지 못함

- **무슨 일**: GA4는 이벤트가 수집돼 목록에 나타난 뒤(최대 24시간)에야 주요 이벤트로 표시할 수 있어서, `study_complete` 지정을 끝내지 못했습니다.
- **교훈**: 플랫폼 처리 지연이 있는 단계는 일정에 미리 넣고, 남는 사용자 작업을 처음부터 안내합니다.

### 5-5. 테스트 방문이 실제 분석 데이터에 섞임

- **무슨 일**: 운영 사이트에 E2E와 연동 확인을 돌려 테스트 방문(미국, `utm_source=qa-check`)과 `study_complete` 이벤트가 GA4에 기록됐습니다.
- **교훈**: 연동 확인은 GTM 미리보기나 GA4 DebugView로 하고, 자동 테스트에서는 분석 스크립트를 막거나 내부 트래픽 필터를 먼저 설정합니다.

### 5-6. 연결 상태를 확인하지 않은 선택지를 제시함

- **무슨 일**: "제 Chrome으로 측정"을 선택지로 냈는데, Claude in Chrome 확장이 연결돼 있지 않아 쓸 수 없었습니다.
- **교훈**: 도구를 선택지로 내기 전에 연결 상태를 먼저 확인합니다.

## 공통 교훈

1. **실행 가능성을 먼저 확인하고 나서 선택지를 냅니다.** 요금제, 공개 여부, 확장 연결처럼 미리 알 수 있는 제약은 질문하기 전에 확인합니다.
2. **판정의 근거를 의심합니다.** 테스트가 실패하거나 결과가 이상하면, 대상보다 측정 방법이 틀렸을 가능성을 먼저 봅니다.
3. **바꾸기 전에 측정하고, 원인을 찾은 뒤에 고칩니다.** 개선 전 기준값은 코드를 바꾸기 전에 확보합니다.
4. **외부 상태를 바꾸는 동작은 처음에 범위를 정해 승인받습니다.** 게시, 배포, 약관, 데이터 오염이 해당합니다.
5. **공유 화면과 외부 콘솔에서는 입력한 뒤 반드시 다시 읽어서 확인합니다.**
